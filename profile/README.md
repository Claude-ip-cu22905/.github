<p>老号和新号能不能共用一个住宅出口？很多教程给的是"尽量分开"，但没说分开之后差别有多大。我们拿六个号做了两周对照：三个老号一组、三个新号一组，一组严格分线跑，一组共线混跑，其余条件全部锁死。记录字段固定为登录结果、是否弹验证、首字节耗时、会话是否中断。下面先交代设计，再给两组原始记录，最后把差异拆开，并给出一套可以直接照做的日常顺序。</p>

<h2>一、实验怎么设：两组六个号，只放开一个变量</h2>
<p>对照实验的价值在于可复现。变量多了，结论就没法归因。这次只让"是否分线"变化，其余全部固定，包括设备、浏览器配置文件的构造方式、每日使用时段和内容类型。</p>
<h3>固定住的四个条件</h3>
<p>同一台机器、同一套浏览器配置文件模板（不装任何改 UA 的扩展）；每天 09:30、14:00、21:30 各操作二十分钟，内容以长文档摘要加三轮追问为主；所有账号都是同一地区的订阅状态；记录只用一个表格，字段为时间、账号、线路、结果、验证次数、首字节耗时。</p>
<h3>两组的差别只有一处</h3>
<p>A 组三个老号各自一条独立住宅地址，全程不换，配置文件和线路一对一绑定。B 组三个新号共用一条住宅地址，用三个不同配置文件轮着登，同一时刻只登一个。两组的地址都来自同一家供应商、同一城市。线路月费区间为每条数十元到两百元（仅供参考），B 组省下两条线的钱。</p>

<h2>二、分开跑的那一组：两周里只有一次验证</h2>
<p>A 组的表现可以用"没有故事"来形容。两周内没有出现 403，没有中途掉线，登录基本一次通过。</p>
<h3>读数：延迟平稳，验证一次</h3>
<p>首字节耗时中位数在 180 到 240 毫秒之间浮动，晚高峰略高但不影响使用。验证只出现一次，发生在第二天，原因是其中一个号换了物理网络（从有线切到 Wi-Fi），属于可解释的变化，重新确认后恢复正常。</p>
<h3>唯一一次异常值得说</h3>
<p>那次验证发生在切换网络的十分钟内。后续我们特意复现了一遍：同一账号在同一条线路上切换物理网络，确实更容易触发确认。这个发现对日常操作有直接意义——固定线路上别随便换本地上网方式。</p>

<h2>三、混跑的那一组：问题从第三天开始堆</h2>

<p>B 组前两天的表现和 A 组几乎一样，这也解释了为什么很多人觉得混跑没问题——前两天确实看不出来。变化从第三天开始。</p>
<h3>第三天：第一次集体验证</h3>
<p>三个号在同一天的不同时段各自弹了一次验证。三个号的内容类型一致、时段也不同，唯一共同点是它们共用同一条地址。这基本坐实了触发源在地址层，而不是单个账号的行为。</p>
<h3>第七天与第十一天：会话中断</h3>
<p>第七天晚上一个号在长对话中途掉线，重进后上下文需要重新建立。第十一天两个号先后出现要求重新登录。这两次都发生在三个号连续交替登录之后，时间间隔不到四十分钟。</p>
<p>顺带说一个反直觉的读数：B 组的首字节耗时反而略好，因为三个号集中在同一条线，带宽利用更充分，中位数落在 170 到 210 毫秒。这说明"快"和"稳"在数据上是两个维度，只看速度会得出错误结论，也是很多人坚持混跑的底气所在。</p>

<h3>第一处：验证次数与地址复用直接相关</h3>
<p>B 组的五次验证里，四次发生在一天内已有其他号登录过的情况下。地址没有变，但使用这个地址的账号在变，这在平台侧看就是同一个网络环境里频繁切换身份。</p>
<h3>第二处：中断来自会话交叉，不是网络</h3>
<p>两次中断时网络层读数正常，<code>mtr</code> 没有明显丢包。问题出在同一个地址下多个会话并存，切换时旧会话的状态没有干净结束。</p>
<h3>第三处：省下的钱被风险吃掉</h3>
<p>B 组每月省下两条线路的费用，大约一百到四百元，但换来的是五次验证和两次中断。按前面拆过的成本口径，这些人工和重建成本已经接近甚至超过省下的金额。</p>

<h2>五、照着做：老号新号的日常操作顺序</h2>
<p>实验结论落到操作上只有几条，都是低成本动作，难的是坚持。</p>
<h3>老号优先占固定线，新号用轮换位</h3>
<p>老号的价值在历史和订阅，给它一条长期不变的地址，别为了腾位置让它搬家。新号可以先共用一条验证用的线做观察，确认状态正常后再分配独立地址，这样可以按实际留存数买线，不必一次买满。</p>
<h3>同一时刻只登一个号，切换留间隔</h3>
<p>如果确实要共用线，至少保证同一时刻只有一个登录态，并且两次登录之间留十分钟以上，退出时走正常登出流程而不是直接关窗口。这两点在 B 组的记录里正好是缺失的。</p>
<h3>账号台账与线路台账合成一张</h3>
<p>一列账号、一列线路、一列最后登录时间、一列异常记录。四个字段足够，关键是每次操作后立刻更新，而不是周末回忆补记。记录一旦滞后，排查就失去依据。</p>

<h2>常见问答</h2>
<h3>老号和新号共用一条线，只是不同时登录，可以吗？</h3>
<p>答：比同时登录好，但仍有风险。实验里 B 组已经做到了不同时登录，仍在第三天出现集体验证。轮流使用能降低冲突，但降低不了"同一地址对应多个身份"这个事实。</p>
<h3>分线之后成本翻倍，小团队怎么承担？</h3>
<p>答：按账号价值分级。涉及订阅和长期历史的老号给独立线，只做测试或短期任务的新号共用少量线。这样既保住核心资产，也不至于一开始就把预算拉满。</p>
<h3>验证弹出来一次，是不是说明这个号已经不行了？</h3>
<p>答：不是。单次验证多数是环境变化触发的例行确认，通过后可以继续用。判断标准是频率：三十天内同一账号或同一线路出现两次以上，才需要考虑换环境。</p>
<h3>两周的结论能推广到更多账号吗？</h3>
<p>答：趋势可以，具体次数不能。账号越多，同一地址上的身份密度越高，问题出现得越早。样本只有六个号，建议按自己的规模先跑一周小样本，再决定配线数量。</p>
